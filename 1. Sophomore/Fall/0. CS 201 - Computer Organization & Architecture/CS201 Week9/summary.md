# CS 201 · Week 9 · Summary

**Topic —** Memory-safety attacks and their defenses, taught defensively: understand the mitigation, then write code that does not need it.
**Lectures —** L28 The Stack Under Attack; L29 Return-Oriented Programming and Control-Flow Integrity; L30 Integer Overflows, Format Strings and the Security Mindset.
**Work —** PS 9 (100, due Week 10, fix-the-bug), Lab 9 (unmarked, sat Tuesday of Week 10), Quiz 9 Monday covering Week 8 (unmarked, key in the paper). **Midterm 2 next week, Weeks 5–9.**
**Takeaway —** Every attack here is an earlier week with a missing check: a buffer overflow is Week 3's frame with an unbounded `strcpy`, ROP is Week 2's instructions reused (libc has 6123 `ret` gadget-endings), a format-string leak reads Week 3's stack, an integer overflow is Week 1's wrap (2⁶² × 4 → malloc(0)). The runtime defenses are real and were all verified on default builds — the canary from `fs:0x28` aborting with "stack smashing detected", NX giving `GNU_STACK RW`, ASLR moving every base each run — but they layer because none is sufficient, and each defense historically motivated the next attack. The constructive answer is upstream: `-fsanitize=address` named the overflow at its exact line and buffer and the use-after-free at both free and misuse, and `-Wformat-security` (in `-Wall`) warns on `printf(user)`. One honesty check the machine forced: `endbr64` CET pads are compiled in but this 2017 CPU does not enforce a shadow stack, so a mitigation being present is not a mitigation being active.
