**Topic —** Type classes: constraints as dictionaries, the standard classes, `Functor` and `Foldable`, and laws the compiler does not check.
**Lectures —** L09 Type Classes: One Function Written Once for Every Type at Once; L10 `Functor`, `Foldable`, and Laws the Compiler Does Not Check.
**Work —** PS 4 (100, fifteen parts, due Friday of Week 5), Quiz 4 (Tuesday, covers Week 3), and **Project 1 assigned Wednesday** — an interpreter for `sq`, 27 tests, three phases, due Friday of Week 7, **15%**. **Lab 3 is sat this Wednesday**; Lab 4 is sat Wednesday of Week 5.
**Takeaway —** A class is a set of types with named operations and a constraint is a requirement on the caller, which compiles to a **dictionary the compiler passes**: `elem :: Eq a => a -> [a] -> Bool` takes two arguments in the source and three in the generated code. Measured — one function, two builds, differing only in a `SPECIALISE` pragma — the dictionary costs about **30%** (2.9 s against 2.2 s at *n* = 2×10⁸), and **deleting the `NOINLINE` as well gives 0.07 s**, roughly 40×, because GHC then inlines, specialises, unboxes and fuses. So the cost is real and usually not paid, and `SPECIALISE` is for the case GHC cannot see across a module boundary. `Num` explains `:t 3`: every integer literal is `fromInteger`, so a literal carries a constraint rather than a type, and `length xs / 2` fails because `Int` is not `Fractional` — the language declining to choose between truncating and true division where **C, Java and Python make three different silent choices**. A class is **not** an interface in four ways, and `mempty :: Monoid a => a` — dispatching on the *return* type, with no receiver — is the one no interface can express; *coherence* (one instance per type, program-wide) is why there is no `instance Monoid Int` and why `Sum` and `Product` are `newtype`s, which is Week 1's free `newtype` finally doing real work. `Functor`'s parameter is a type *constructor*, so `Maybe` is the functor and not `Maybe Int`; `<$>` is `fmap` infix. **`Foldable` needs one method** — `foldr` or `foldMap` — and gives you twenty, which is why `Foldable t =>` has been in every `:t` since Week 0; and it brings the traps: `length (Just 3)` is 1, `length ('x', 5)` is **1**, `maximum ("hello", 3)` is **3** because a tuple is foldable in its second component only, `maximum (Left "x")` **throws** while `length (Left "x")` is 0, and `null (Just undefined)` is `False` without forcing anything. **But the week's real content is that instances carry laws and nothing checks them.** A `Functor` instance that swaps its subtrees compiles `-Wall` silent and breaks both laws — and only a *value*-symmetric tree hides it, which `fromList` cannot even build because `insert` drops duplicates. Worse, setting `mempty = Stats 0 0 999` — plainly not an identity for `max` — leaves **all ten of Lab 4's law checks printing `ok`**, because `a = foldMap statsOf …` seeds with `mempty` and **the broken value contaminated its own test data**; the check that catches it must build a `Stats` through `statsOf` instead. A test written in terms of the thing it tests cannot see the thing it tests, which is the premise of Week 11.
**New syntax —** `class C a where` · `instance C T where` · `class B a => C a` superclasses · `<$>` · `<>` · `mempty` · `{-# MINIMAL … #-}` · `{-# SPECIALISE #-}` · `{-# LANGUAGE InstanceSigs #-}`; and `fmap` `foldMap` `mconcat` `stimes` `toList` `Sum` `Product` `Max` `Min` `Complex`.
