# CS 212 · Week 3 · Summary

**Topic —** Architecture: what it is and when it is decided; layered, hexagonal and MVC; microservices and event-driven; and where an invariant actually lives.
**Lectures —** L10 What Architecture Is, and When It Is Decided; L11 Layered, Hexagonal, and MVC; L12 Microservices and Event-Driven — What They Buy, and the Bill.
**Work —** A 2 due Friday 17:00; A 3 released Wednesday (100, due Friday of Week 4); **Quiz 3 Tuesday** (unmarked, covers Week 2); **four ADRs and an architecture test committed to the team repository**.
**Takeaway —** Architecture is the set of decisions that are expensive to reverse, and the test — *what would changing this cost in March?* — sorts most of what teams argue about into the half not worth having. **You have an architecture whether or not you decide one**, and the undecided one is always the same: logic in the handlers, SQL wherever convenient, rules everywhere — which is `roomsvc`, chosen by nobody. Quality attributes conflict and must be ranked with a sacrifice named; for a five-person term project the honest order starts at testability and ends at scalability, and a team ranking scalability first will build the wrong system for 34 rooms. ADRs are the highest-value process artefact here: immutable, with negatives, with the alternatives and why they lost, in git — **and the record of having changed your mind is the most valuable part.** **The invariant question finally gets its answer: the database.** Not the UI (`curl` ignores it), not the API layer (it cannot see concurrent requests), not the domain layer (that is check-then-act, which is `confirm_booking`), not an in-process lock (you run four workers) — **the domain owns the rule and the database owns the guarantee**, and the general form is that an invariant must be enforced at the narrowest point every path must pass through. Layering's stated rule is that a layer calls the one below; **the unstated rule — a layer does not know the layer above exists — is the one that carries the value**, and twelve lines of `ast` in CI turns it from a hope into a rule. Hexagonal defines ports from the inside and buys fast tests (1 ms against 1.2 s per module) and a readable domain, **not database portability**; only the driven side needs inversion, and the test fake is a first-class adapter. MVC is a 1979 user-interface pattern whose core observer relationship HTTP does not have, so *"we use MVC"* answers nothing and usually means an anemic model and a fat controller. Microservices buy exactly one thing — **independent deployability by separate teams** — and the bill is the lost transaction, sagas whose compensation is not undo, partial failure with its retries and idempotency, seven logs, eight containers, **and refactoring across a boundary becoming a migration at precisely the moment your domain model is least reliable.** Event-driven buys extension without modification and temporal decoupling, and costs the ability to answer *"what happens next?"* by reading; one subscriber is a function call wearing a costume. **The week's portable sentence: a rule a machine checks is a rule; a rule in a diagram is a hope — so add the test while your violation count is still zero.**
