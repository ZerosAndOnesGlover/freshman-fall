**Takeaway —** The *"review finds 60% of defects"* figure comes from **Fagan inspection** at IBM in the 1970s — three to six people, hours of solo preparation, a reader paraphrasing aloud, **150 lines per hour**, defects logged rather than solved, and a follow-up stage — which is a different activity from a pull request with the same name, and transferring the number is the field's commonest evidential error. **Bacchelli & Bird's 570 comments** show defect finding ranked first in expectation and delivering about **14%** in practice, behind code improvements at **29%**: the real value is knowledge transfer, team awareness and readability, which nobody lists when asked. Four reasons survive — **more than one person has read it** (`roomsvc`'s bus factor on `bookings.py` is 1, 78% of surviving lines by an author who left in 2023, and the four-month fix was four months of nobody willing to touch it), knowledge transfer, readability made observable, **and a choke point where automated checks can be applied.** How to review is better evidenced than why, and it is one variable: **size.** Cisco — defect density collapses above 200 lines, effectiveness above 60 minutes; Google — **median change ~24 lines, one reviewer, first response under an hour.** Big reviews fail because attention exhausts, a large diff exceeds working memory, **and social pressure means reviewers approve them.** Review costs 10–15% of engineering time plus latency, and **PRs awaiting review are work in progress**; the free fix is *review before you write*. The standard for approval is **definitely improves code health, even if imperfect** — not *ideal*, not *how I would have written it* — **but push back hard on design**, because that is what is expensive to reverse. The checklist's order is its content: should this exist → **design** → correctness → tests → readability, because reviewers left alone start at line 1 and never reach design; **the single best question is "is there a test that fails without this change?"** Never comment on formatting, anything a linter catches, unjustified style preferences, or the person. **Label severity — `blocking:` / `question:` / `nit:` / `praise:`** — four characters, without which fourteen nits read as a rejection. Three hard cases: *"rewrite this"* is a process failure not a comment, *"I don't understand this"* is a **finding**, and **anything recurring belongs in CI.** Automation is a **budget reallocation**, not rigour: five layers cheapest-first, with **custom rules the one nobody writes and the highest-value**; type checking finds real defects with no test, though the 15% figure is about JavaScript; scanners earn on dependency audits and secrets and waste on general rule sets; **and no tool can check whether the requirement is right, the responsibility placed right, the code comprehensible, or the concurrency safe — the VNC 101 race passes all five layers.** **Never block on a probabilistic check**, because a gate wrong two times in five gets removed and then you have neither the gate nor the advice.
