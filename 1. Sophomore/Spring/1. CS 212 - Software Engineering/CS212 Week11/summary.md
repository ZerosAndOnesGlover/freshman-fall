# CS 212 · Week 11 · Summary

**Topic —** Technical debt, software metrics, maintainability and documentation: what to measure, what to ignore, and what to write down.
**Lectures —** L34 Technical Debt — the Metaphor, and Its Abuse; L35 Metrics That Mislead, and Metrics That Help; L36 Documentation That Survives.
**Work —** A 10 due Friday 17 April 17:00; A 11 released Wednesday (100, produces `docs/debt.md`, due Friday 24 April); **Quiz 11 Tuesday — the last quiz.**
**Takeaway —** Cunningham's 1992 metaphor is two pages and describes a **deliberate financing decision** in which the thing owed is **understanding** — code that does not yet reflect what you have since learned — so **what the industry calls technical debt is mostly mess, and the word is how mess gets excused.** Fowler's quadrant separates deliberate from inadvertent and reckless from prudent: prudent/deliberate is Cunningham's and needs a trigger; **prudent/inadvertent is the most common and most honest**; reckless/inadvertent is an education problem; reckless/deliberate is not debt. **Interest, not principal, decides priority — and interest = badness × touch frequency**, the second factor being in your `git log` and requiring no judgement, so **terrible code nobody touches costs nothing**: `legacy_import.py` is worse than `calendar_sync.py` and not worth a day. A register entry needs six fields, of which *"why we took it on"* distinguishes debt from mess and *"interest"* enables prioritisation; **a trigger beats a date**, because a trigger fires when the cost is actually being paid, which is when repayment is cheapest. **Four times not to repay**: untouched code, a component being replaced, a repayment riskier than the debt, **and the last fortnight of a project — which is now.** Debt is not only code: test, documentation, API, process, dependency, data and knowledge debt all belong on the register, **and dependency debt is the only kind that accrues while you sleep.** **Goodhart's law has now appeared five times in eleven weeks**, and the mechanism is never dishonesty — **a measure is a proxy, and optimising a proxy diverges from the goal exactly where the proxy is weakest** — so measure, read, act on individual findings, and **never set a target; the one legitimate target-shaped use is a ratchet.** Lines of code as productivity is uniquely bad, since deleting 380 lines is one of the best available changes and scores −380; cyclomatic complexity is a threshold alarm and tells you the minimum test cases for branch coverage; **the maintainability index is a 1991 formula with arbitrary weights that cannot be acted on**; velocity is the most abused number in the field and **cycle time is the honest alternative.** **Hotspots — change frequency × complexity — beat every static measure**, because the `git log` supplies the dimension a static analyser cannot see; **change coupling finds couplings that exist in no import graph** (112 of 891 commits, neither file importing the other) and **`git blame` finds the bus factor of 1 on the file absorbing 41% of all change.** **Read every number as a trend rather than a score**: a trend is robust to a bad measure, implies an action, and catches deterioration a threshold hides. **Documentation rots structurally** — code is executed and cannot silently become false, prose is not and does — so it survives in proportion to how close it lives to the code and how much a machine checks; **generate reference, and write explanation**, which is the only kind that does not rot and the only kind unrecoverable from the code. Six kinds are machine-checked — types, tests as specification, executable examples, **the architecture test**, generated reference, **and a README quickstart run in CI**; four must be prose, and **a comment explaining *why* is an artefact while one explaining *what* is a naming failure.** **The onboarding test is the one empirical measure.** And the honest closing note: eleven weeks of measurement, and **the most important property of the system is verified by one integration test and one line of DDL, neither of which appears in any metric you report.**
