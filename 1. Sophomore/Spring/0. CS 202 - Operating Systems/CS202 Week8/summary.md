**Takeaway —** One file-system operation is several block writes, and the file system does not control the order in which they reach the disk, so a crash can leave a state no operation intended: stopping `myfs` after every possible number of writes left **36 of 93 crash points inconsistent** — two crash points in a `create` orphaned an inode, and 34 in an 8 KiB `write` leaked blocks — while **no interrupted operation ever left the completed result**. `fsck` can restore consistency but not correctness, and its cost is a scan of the whole disk. A journal reduces the problem to a single block write: log the new contents, write the commit header, install, clear — after which **0 of 118 crash points left `myfsj` inconsistent**, 20 of them recovering into the finished operation, while **skipping recovery broke 14 of 112**, making a journal without replay worse than none. The log costs a second write per logged block, measured at **1.23× for an 8 KiB write and 2.3× for a `create`**, the difference being absorption and the two header writes; xv6's `log.c` adds batching across system calls, and ext4 journals metadata only, ordering data before it. Copy-on-write is the other answer: measured on qcow2, a snapshot of a 64 MiB image cost **196 KiB**, reads fall through to the backing file, and the first write to a region copies a whole cluster — **16× amplification at 64 KiB clusters, 1.5× at 4 KiB, and 21% more latency** — while snapshots pin blocks that deletion then cannot free. Finally, ext4 checksums its metadata and caught a single flipped byte in the inode table, and **silently returned a corrupted file byte with a clean `fsck`** when the same flip was made in data, which is the case ZFS's end-to-end checksums exist for.
