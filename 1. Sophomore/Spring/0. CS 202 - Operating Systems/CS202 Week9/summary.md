**Takeaway —** One system call reaches every device through a table of function pointers — nine lines of `devsw` in xv6, a page of `file_operations` in Linux, where the extra entries are `open`, `ioctl`, `poll` and `mmap`, and `ioctl` is the admission that not everything is a read or a write. What that dispatch costs was measured with a driver that does nothing: a write to `/dev/null` took 659 ns, an `ioctl` returning an error 595 ns, and a 4 KiB read of `/dev/urandom` 12,689 ns — so small I/O is dominated by the system call, and only `/dev/urandom`'s 2.9 ns per byte is the device's own work. Below that, request size decides everything: reading the same 256 MiB with `O_DIRECT` took 1,969 interrupts and 0.14 s in 1 MiB pieces — one interrupt per 128 KiB, which is exactly `max_sectors_kb` — against 65,536 interrupts and 1.1 s in 4 KiB pieces, on a device with eight hardware queues, 1,023-deep, and no I/O scheduler because it has no seek to optimise. A handler may not sleep, which forces the top-half/bottom-half split and the spinlock discipline of Week 3. Writing the driver twice made the boundary concrete: the Linux module builds — 330 KB of object file, 1,604 bytes of it code — and `insmod` refuses it with "Operation not permitted", because a loaded module is the kernel; the same ring buffer in xv6 registers in `devsw`, blocks in `sleep` until a writer arrives, and read 300 and 1,000 bytes back in order.
