**Takeaway —** A virtual machine is Week 0's wall placed around a whole kernel: the guest runs in VMX non-root mode, and the instructions that would touch real hardware cause VM exits instead. On Linux the privileged part is a driver — `/dev/kvm`, API version 12 here, offering 8 recommended vCPUs and 32,764 memory slots — and the hypervisor itself is an ordinary program: about 120 lines create a VM, install a `mmap` as the guest's physical memory, create a vCPU, set it to 16-bit real mode, and run it, whereupon a guest of fifteen hand-assembled bytes printed a string through port 0x3f8 in 21 exits. Guest physical memory being host virtual memory means everything from Weeks 5 and 6 applies to it, and EPT translates guest physical to host physical in hardware, at the price of a TLB miss that can touch 24 lines of page table. A device is simply a hole in that memory: the guest's write to an unbacked 0x80000 returned an MMIO exit carrying address, length, direction and data. What all of this costs was measured: an exit KVM answers inside the kernel costs 1,409–1,464 ns, one that reaches the hypervisor process costs 7,778–7,880 ns — 5.5× — creating a VM costs 152–493 µs and destroying one 10.8–11.5 ms, nearly all teardown. And xv6 booted in 1.20–1.29 s under software emulation against 0.92–1.17 s under KVM, barely faster, because its boot is emulated device registers rather than computation — which is why every real optimisation removes exits instead of shortening them: in-kernel devices, coalesced MMIO, virtio's queue in shared memory, or passing the hardware through. Containers isolate differently, with namespaces and cgroups over one shared kernel and no exits at all; this machine allows the cgroup half and refuses the namespace half, since AppArmor blocks unprivileged user namespaces.
