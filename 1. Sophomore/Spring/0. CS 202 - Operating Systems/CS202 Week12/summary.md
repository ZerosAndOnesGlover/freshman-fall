**Takeaway —** Security is the first week of this course to assume an adversary rather than bad luck, which changes the question from "how fast" to "what does a failure yield". The trusted computing base is larger than it looks and can be counted: 18 setuid or setgid binaries among 2,049, four more carrying file capabilities, plus the loader, libc and the toolchain — and `pkexec`, on that list, was exploitable for twelve years without any kernel bug. A reference monitor must mediate completely, resist tampering, and be small enough to verify; hardware supplies the first two and no general-purpose kernel supplies the third, so what the industry does instead is layer mitigations that leave the bug in place. Measured here: one `strcpy` overflow was caught by `_FORTIFY_SOURCE` before the copy, by the stack canary at the return, and by nothing at all in a third build where control had already transferred — and an early version of that experiment compared the wrong two builds and measured fortify twice. ASLR gave 200 distinct layouts in 200 runs, about 2²² pages for the stack and 2³² elsewhere, but the code-to-data offset never changed, so one leaked address discloses the whole image, and `setarch -R` turns it off on request. A timing channel in ordinary correct code leaked 2.5 ns per byte over a 1.25 ns noise floor and yielded exactly one byte of an eight-byte secret, which is the honest form of the claim: exploitability is quantitative. Least privilege is the one principle that does not assume the code is correct, and on this machine it costs about 50 ns per system call — about 6% — independent of how many rules the filter has or how many filters are stacked, because the cost is the check and not the rules. The policy itself cannot be written from first principles: an allowlist built from what a program obviously needs kills it before `main`, because glibc calls `rseq`. And two mechanisms that appear to do one job are not interchangeable: `RLIMIT_NPROC` counts the user's 1,068 threads and refuses at zero children, while a cgroup's `pids.max` of 20 allows exactly 19. The course closes on its own two habits: the Week 0 claim re-tested twelve weeks later, where `sgdt` still hands an unprivileged program a live kernel address on a kernel built with `CONFIG_X86_UMIP=y` because the CPU has no UMIP; and the term's own broken harnesses, whose common form was never an error message but a plausible number.
