## 2. The Compiler Writes Functions For You

If you do not declare them, the compiler declares and defines these for your class:

| Function | Signature | What the generated one does |
| --- | --- | --- |
| Default constructor | `T()` | Default-constructs each member. **Only if you declare no constructor at all** |
| **Copy constructor** | `T(const T&)` | **Copies each member** |
| **Copy assignment** | `T& operator=(const T&)` | **Assigns each member** |
| Destructor | `~T()` | Destroys each member |

*(C++11 adds move construction and move assignment. Those are Week 5.)*

So the function that ran was `CharBuffer::CharBuffer(const CharBuffer&)`, generated by the compiler,
and it performed a **memberwise copy**.

### 2.1 Memberwise Copy Is Usually Right

`Vector3D` from Lecture 04 has one member, `double e[3]`. Memberwise copy copies the array element by
element, producing a fully independent vector. Verified:

```
c[0]=99 -> c = (99, 2, 3)   a = (1, 2, 3)  (independent)
```

**`Vector3D` needs no copy constructor, no copy assignment and no destructor**, and adding them would
be strictly worse — more code, more to get wrong, and no behaviour change.

> **This is the majority case.** Most classes should declare none of these. The rule at the end of this
> lecture is about the minority that must.

### 2.2 And For `CharBuffer` It Is Catastrophic

```cpp
class CharBuffer {
    int   size;
    char* data;
    // ...
};
```

Memberwise copy of `data` copies **the pointer**, not what it points at:

```
        a                      b
   ┌──────────┐           ┌──────────┐
   │ size = 8 │           │ size = 8 │
   │ data ────┼─────┐     │ data ────┼─────┐
   └──────────┘     │     └──────────┘     │
                    ▼                      ▼
              ┌───────────────────────────────┐
              │  one heap allocation, 8 bytes │
              └───────────────────────────────┘
```

Two objects, two destructors, **one allocation**. The first `delete[]` succeeds; the second is a
double free.

**The compiler is not wrong here — it is uninformed.** `char* data` does not say whether this object
*owns* that memory or merely *observes* it. If `CharBuffer` were a non-owning view into someone else's
buffer, copying the pointer would be exactly correct. The type system cannot tell the two apart, so the
compiler picks the one that is right more often and cheaper.

**Deciding is your job, and that is what the Rule of Three is for.**

## 3. Shallow and Deep

| | Copies | Result |
| --- | --- | --- |
| **Shallow copy** | The pointer | Two objects sharing one allocation |
| **Deep copy** | The pointed-to data | Two objects, two allocations, independent |

The generated copy constructor is always shallow with respect to anything behind a pointer. If your
class owns heap memory, you want deep.

---

## 4. The Rule of Three

> **If a class needs any one of: a destructor, a copy constructor, or a copy assignment operator —
> it almost certainly needs all three.**

The reasoning is a single chain:

1. A user-written **destructor** means the object *owns* something it must release.
2. If it owns something, a **shallow copy** produces two owners of one resource.
3. Two owners means **double release** on destruction, and a leak or corruption on assignment.
4. Therefore an owning class must define **how it is copied** — both ways it can be copied.

**The destructor is the tell.** When you find yourself writing `~T()` with a `delete` in it, stop and
write the other two.

### 4.1 Or Explicitly Refuse

Sometimes copying makes no sense — a file handle, a mutex (Week 10), a `unique_ptr` (Week 5). Then say
so:

```cpp
CharBuffer(const CharBuffer&)            = delete;
CharBuffer& operator=(const CharBuffer&) = delete;
```

This is **also** satisfying the Rule of Three. The rule says decide, not implement. A class that
forbids copying is safe; a class that leaves it to the compiler is not.

## 5. Writing the Copy Constructor

```cpp
CharBuffer(const CharBuffer& other)
    : size(other.size),
      data(new char[other.size])            // a NEW allocation
{
    std::memcpy(data, other.data, size);    // copy the contents
}
```

Three things to notice:

- **Takes `const CharBuffer&`.** It must be a reference — taking it by value would require a copy to
  construct the parameter, which would call the copy constructor, infinitely. The compiler rejects it.
- **Allocates before copying.** `data` is a fresh allocation; nothing is shared.
- **Uses the initializer list**, in declaration order (L02 §4).

---

## 6. Writing Copy Assignment — And Getting It Wrong

Assignment differs from construction in one crucial way: **the target already exists and already owns
something.** So there are four steps, not two:

```cpp
CharBuffer& operator=(const CharBuffer& other) {
    delete[] data;                          // 1. release what we have
    size = other.size;                      // 2. take their size
    data = new char[size];                  // 3. allocate
    std::memcpy(data, other.data, size);    // 4. copy their contents
    return *this;                           // for chaining: a = b = c
}
```

This is deep, it releases the old buffer, and it looks right.

**It is broken.**

---

## 7. Self-Assignment, Traced

```cpp
Buf a("hello");
a = a;
```

Nobody writes that deliberately. Everybody writes `v[i] = v[j]`, and sometimes `i == j`.

Here is the operator instrumented to print what it does, with `Buf a("hello")`:

```
  enter: this=0x750a50700020  &o=0x750a50700020  same object? YES
  old d=0x502000000010 contents="hello"
  n=6 (a member, not in the freed block -- survives)
  new d=0x502000000030   o.d=0x502000000030  <- o.d IS the new pointer
  after memcpy, bytes: be be be be be be
  any NUL terminator? NO
```

Follow it:

1. **`delete[] d`** frees the block holding `"hello"`. That data is now gone.
2. **`n = o.n`** reads 6 and works fine — `n` is a member of the object, not inside the freed block.
3. **`d = new char[6]`** installs a fresh pointer. Since `o` *is* `*this`, **`o.d` is now that same new
   pointer.**
4. **`memcpy(d, o.d, 6)`** copies the new uninitialized buffer onto itself. It is a no-op over garbage.
5. The result is six bytes of `0xbe` — AddressSanitizer's fill pattern for fresh allocations — with
   **no NUL terminator**.

Then `printf("%s")` runs off the end:

```
ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000036
READ of size 7 at 0x502000000036
0x502000000036 is located 0 bytes after 6-byte region [0x502000000030,0x502000000036)
```

### 7.1 Note What This Is Not

**It is not a use-after-free.** The freed block at `0x502000000010` is never read. Step 3 replaced the
pointer before anything looked at it.

Textbooks usually describe self-assignment as a use-after-free, and for some implementations it is.
For *this* one the failure is subtler: **the data is silently destroyed and replaced with garbage**,
and the crash happens later, somewhere else, in whatever code first reads the string.

> **That is a worse bug than a use-after-free**, because it separates the cause from the symptom. The
> corruption happens in `operator=`; the crash happens in `printf`. Without a sanitizer, you would be
> debugging the wrong function.

## 8. The Guard

```cpp
CharBuffer& operator=(const CharBuffer& other) {
    if (this == &other) return *this;       // <-- the fix
    delete[] data;
    size = other.size;
    data = new char[size];
    std::memcpy(data, other.data, size);
    return *this;
}
```

Verified:

```
Naive    -> AddressSanitizer: heap-buffer-overflow
Guarded  -> "hello"
```

**This is correct, and it is not the best answer.** Two objections:

1. **It pays a comparison on every assignment** to defend against a case that is rare. Not a serious
   cost, but it is backwards — the common path pays for the rare one.
2. **It is still not exception-safe.** If `new char[size]` throws, `data` has already been `delete[]`d
   and `size` already overwritten. **The object is left destroyed** — not unchanged, not valid, just
   broken. Its destructor will then run on a dangling pointer.

Point 2 is the real problem and it is invisible until Week 9. Lecture 06's copy-swap idiom fixes both
in three lines, and gets self-assignment safety without ever comparing addresses.

## 9. Your Compiler Will Not Warn You

This is the part worth remembering, because it is uncomfortable.

**The course's own development build line does not catch this bug.** A class with a destructor, a
`char*` member, and no copy constructor compiles **silently**:

```
g++ -std=c++17 -Wall -Wextra -pedantic -g -fsanitize=address,undefined dep.cpp
    (no output)
```

Two flags do catch it.

**`-Wdeprecated-copy-dtor`** reports that the generation is deprecated:

```
warning: implicitly-declared 'constexpr Buf::Buf(const Buf&)' is deprecated
         [-Wdeprecated-copy-dtor]
note: because 'Buf' has user-provided 'Buf::~Buf()'
```

Note the wording: the copy constructor is **still generated**. The standard deprecated this in C++11
and has not removed it, because doing so would break an enormous amount of existing code.

**`-Weffc++`** — named after Meyers' *Effective C++* — states the rule directly:

```
warning: 'class Buf' has pointer data members [-Weffc++]
warning:   but does not declare 'Buf(const Buf&)' [-Weffc++]
warning:   or 'operator=(const Buf&)' [-Weffc++]
```

**Measured on this week's code, `-Weffc++` produced zero false positives**: no warnings on `Vector3D`
(which owns nothing and correctly declares none of the three) and no warnings on a `Buf` that declares
all three. It fired only on the broken class.

> **Worth adding to your own builds.** It is not in the course build line because it is stricter than
> the standard and complains about some legitimate designs in larger codebases. On the small classes
> you write this semester it is close to free, and it catches exactly the mistake this lecture is
> about.
>
> The general lesson is bigger than one flag: **`-Wall -Wextra` is a floor, not a ceiling.** A clean
> build is not a correct program, and the most dangerous defaults are the ones that compile quietly.

## 10. The Complete Class

```cpp
class CharBuffer {
    int   size;
    char* data;
public:
    explicit CharBuffer(int n)
        : size(n), data(new char[n]) { std::memset(data, 0, size); }

    CharBuffer(const CharBuffer& o)                        // 1. copy constructor
        : size(o.size), data(new char[o.size]) { std::memcpy(data, o.data, size); }

    CharBuffer& operator=(const CharBuffer& o) {           // 2. copy assignment
        if (this == &o) return *this;
        delete[] data;
        size = o.size;
        data = new char[size];
        std::memcpy(data, o.data, size);
        return *this;
    }

    ~CharBuffer() { delete[] data; }                       // 3. destructor
};
```

All three present. No double free, no self-assignment corruption, and still **not exception-safe** —
which is Lecture 06.

---

## 11. Summary

| Idea | The point |
| --- | --- |
| The compiler generates four special members | Including copy construction and copy assignment |
| The generated copy is **memberwise** | Correct for values, fatal for owned pointers |
| Shallow vs deep | Shallow copies the pointer; deep copies the data |
| **Rule of Three** | Destructor, copy constructor, copy assignment come as a set |
| `= delete` also satisfies it | The rule says *decide*, not *implement* |
| Copy assignment has four steps | Release, take, allocate, copy — construction has two |
| Self-assignment breaks the naive version | Traced: data destroyed, no terminator, `0xbe` bytes |
| It is **not** a use-after-free | The freed block is never read — the cause and crash are separated |
| The guard works but is not best | Costs the common path; still not exception-safe |
| **`-Wall -Wextra` does not catch this** | `-Weffc++` does, with no false positives on this week's code |
